09-29: **처리 완료 알림**(`run.py`의 `notify()`, macOS `osascript`)은 구현 완료 - 전사~품질 루프까지 다 끝나고 검토 화면을 열기 직전에 뜬다. **브라우저를 먼저 여는 것(처리 중 진행 화면)은 이번엔 범위 밖으로 남겼다** — `Session.__init__`이 `transcript.json` 존재를 전제하고 있어(없으면 즉시 실패), 처리 시작과 동시에 서버를 띄우려면 Session이 "아직 처리 중"인 부분 상태를 견디도록 바꿔야 하고, `run.py`가 지금처럼 각 단계를 순차 `subprocess.run(check=True)`로 끝난 뒤 서버를 마지막에 여는 구조도 동시 실행 구조로 재설계해야 한다 — 라이브 브라우저 테스트 없이 하기엔 회귀 위험이 커서 미룸.

10-01(worktree): **브라우저를 먼저 여는 것**도 끝냈다 - 걱정했던 두 가지를 둘 다 좁게 풀었다.
1. `server.py`: `transcript.json`이 없어도 `ThreadingHTTPServer`가 즉시 bind한다 - `Handler.session`을 `None`으로 두고 백그라운드 스레드가 1초마다 `Session(folder)` 생성을 재시도, 성공하면 교체. `self.session is None`인 요청은 정적 페이지 셸 + 확장된 `/api/status`(`ready`/`stage`/`done`/`total`/`state`/`error`, `edit/pipeline_status.json`에서 읽음)만 응답하고 나머지는 503 - `AttributeError` 없음. 이미 다 처리된 폴더는 여전히 즉시 `Session`이 만들어져 진행 화면이 전혀 안 보인다(회귀 없음)
2. `run.py`: 폴더 확정 직후 `server.py`를 `start_new_session=True`인 detached 백그라운드 subprocess로 띄우고(브라우저 오픈은 서버 자신이 bind 후 처리) 그다음에야 파이프라인 단계를 돈다 - `step()`이 매 단계 끝에 `edit/pipeline_status.json`을 쓴다. `--serve`는 그대로(동기, 변경 없음)
3. `web/index.html`: `/api/session`을 부르던 bootstrap(`load()`) 앞에 `pipelineBoot()`를 두어 `/api/status`로 준비 여부를 먼저 확인 - 안 됐으면 최소 진행 화면을 그리고 1초마다 재확인, `ready`가 true가 되면 `location.reload()`로 평소 경로를 그대로 탄다

검증은 curl로 세 경로(처리 중 bind, 손으로 쓴 `pipeline_status.json` 반영, `transcript.json` 복원 후 세션 전환)와 이미 처리된 폴더의 무회귀를 확인했다 - **라이브 브라우저로 시각 확인은 아직 안 됨**(이 환경에 Playwright 등 브라우저 자동화가 없음). 실제 진행 화면 렌더링·폴링·reload가 매끄러운지는 실제 촬영으로 한 번 사람이 봐야 한다.

- **처리 완료 알림**: 전사·분류가 끝나면 macOS 알림 + 브라우저 자동 열기. `osascript` 한 줄
- **브라우저를 먼저 연다**: 처리 중에도 검토 화면을 띄우고 단계별 진행을 보여준다 (`/api/status` 이미 있음). 전사만 끝나면 본문은 먼저 읽을 수 있다
