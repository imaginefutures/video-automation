`/`에 영상 목록: 상태(처리 중 / 검토 중 N건 남음 / 확정 / 미리보기 준비됨), 확정일, 검토 시간. 클릭하면 이어서 검토. 촬영 공백 뒤 돌아와도 "어디까지 했더라"가 없다. 첫 진입 시 단축키 카드를 한 번 보여준다.

## 구현 메모 (10-01)

- `scripts/home_server.py` + `web/home.html` - `scripts/server.py`(영상 하나당 프로세스 하나가
  전제인 구조, `Handler.session`이 폴더 하나만 가리킴)는 건드리지 않고 별도 프로세스로 뒀다.
- 상태 스캔은 `Session`을 만들지 않고 `ng.json`/`decisions.json`/`speaker_blocks.json`/
  `actions.log`만 직접 읽는다 - `_display_route`/`_ng_status`/`_block_status`/
  `_review_estimate`/`_pref_action_for_case`(개인화 정답지, `~/.video-cut/prefs/<user>.json`)와
  같은 규칙을 가볍게 복제했다. **server.py가 이 규칙들을 바꾸면 home_server.py도 같이 고쳐야
  한다** - 자동으로 동기화되지 않는다(디자인 트레이드오프, 아래 "구조적 제약" 참고).
- "클릭하면 이어서 검토": 홈 서버가 그 영상 전용 `scripts/server.py`를 새 포트(8766~)에
  띄우고(이미 떠 있으면 재사용) 브라우저를 그 포트로 보낸다. "영상 하나당 서버 프로세스
  하나"라는 기존 전제를 유지하면서 홈 화면만 얹은 것 - 서버를 다중 세션으로 확장하는 더
  침습적인 방법은 택하지 않았다.
- `web/index.html`은 건드리지 않았다(병렬로 P4 재설계 중이라 충돌 방지).

### 구조적 제약 (server.py가 영상 하나만 다루는 구조라서 생긴 것)

- 홈 서버가 죽으면(`pkill`처럼 SIGTERM으로 강제 종료 시) 띄워 둔 영상별 server.py 프로세스가
  고아로 남는다 - `atexit`로 정리하지만 SIGTERM 기본 처리는 atexit를 안 거치고 바로 죽는다
  (Ctrl+C처럼 정상 종료할 때만 동작). 기존에 `run.py --serve`를 터미널에서 손으로 띄울 때도
  같은 성격의 문제가 있었으니 새로 생긴 리스크는 아니지만, 세션 수가 늘면 눈에 띌 수 있다.
  제대로 고치려면 서버가 포트별로 뜬 자식들을 PID 파일 등으로 추적해 홈 화면에서 "중지"까지
  관리해야 하는데, 이번 1차 구현 범위 밖으로 남겨뒀다.
  - **상태 계산 로직 이중화**: `server.py`의 `_display_route`/`_ng_status`/`_pref_action_for_case`
    등을 import하지 않고 복제한 건 Session 생성 비용(ffprobe 등)을 피하려는 의도적 선택이지만,
    두 파일이 갈라질 위험을 남긴다. 검증 결과 지금은 일치한다(BS145/167/183 실측, 아래 참고).
