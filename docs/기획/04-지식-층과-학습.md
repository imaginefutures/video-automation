# 04. 구조적 버그 탐지 — 사용자 피드백에서 보편적 버그를 찾는 법

**2026-10-01 전면 개정**: 이 문서의 이전 버전(L0~L3 지식 층, L1 사용자 규칙, L2 사용자 사례 기반
few-shot 개인화, "쓸수록 똑똑해지는 게 보이게")은 **폐기한다**. 개인화 설계 전체를 걷어내고, 사용자
피드백을 **개인 취향이 아니라 보편적 버그를 찾는 신호**로만 쓰는 쪽으로 바꾼다. 이전 버전은
`결정-이력.md` 2026-10-01 항목과 `../채택하지-않은-것.md`에 왜 버렸는지 남겨뒀다.

---

## 1. 왜 바꿨나

실제로 발견된 사례로 설명한다. 사용자가 기존 테스트 영상 여러 편에서 **"삭제 구간 바로 뒤에 접속사로
시작하는 새 문장이 오면 그 접속사까지 같이 잘린다"**는 패턴을 반복해서 복원했다. 이건 이 사용자의
취향이 아니라 **모든 사용자가 겪을 경계 판정 버그**다(`classify_region.py`의 wi_end가 실제 경계를
넘어가는 것 — `final_attempt_wi_start` 클램프와 같은 버그 종류지만 다른 구조적 맥락, 상세는
[`../미결-사항.md`](../미결-사항.md)).

**만약 폐기된 설계(L1/L2 개인화)가 완성된 상태였다면 무슨 일이 났을까**: 이 반복된 복원은
`prefs.json`의 해당 케이스 cut/keep 통계에 조용히 쌓이고, "이 사용자는 접속사를 복원하는 걸
좋아하는구나" 정도로 흡수됐을 것이다. 버그는 고쳐지지 않고 **이 사용자 계정에만 땜질**되고, 다른
사용자나 다음에 새로 설치한 사람은 똑같은 버그를 처음부터 다시 겪는다.

이 사례가 드러낸 구조적 결함은 세 가지다.

1. **구분 장치가 없다**: 사용자의 모든 복원/추가삭제를 "개인 취향 신호"로 똑같이 취급했다. 그중
   상당수는 사실 **엔진이 보편적으로 틀린 것**인데, 개인화 통계가 이 둘을 구분하지 못하고 전부
   흡수한다.
2. **임계값이 통계적으로 얇다**: `_pref_action_for_case()`의 `PREFS_MIN_SAMPLES=3`,
   `PREFS_MIN_RATIO=0.75`는 한 영상의 특이한 맥락(우연)만으로도 넘을 수 있는 기준인데, 넘으면
   승인 화면 없이 곧바로 미래 라우팅을 바꾼다. `reverts` 추적은 있지만 사후약방문이라, 틀린 자동
   적용이 이미 몇 번 일어난 뒤에야 꺼진다.
3. **효과를 검증할 방법이 없다**: 컷 엔진 본체는 BS145/167/183 gold 대조로 정밀도·재현율을 실측해
   검증하는데, "개인화가 실제로 복원율을 낮췄는가"는 그런 객관적 정답지가 없고 사용자가 실제로 여러
   영상을 몇 주 써야만 알 수 있다. 검증 불가능한 로직을 자동 라우팅에 반영하는 건 이 서비스의
   "안전 지표가 최우선" 원칙과 맞지 않는다.

**결론**: 사용자 피드백은 계속 모으되, 그 피드백으로 할 수 있는 건 **"이 패턴이 버그처럼 보인다"고
개발자에게 알리는 것뿐**이다. 미래의 자동 CUT/KEEP 판단을 사용자별로 조용히 바꾸는 경로는 전부
없앤다.

## 3. 새 설계: 구조적 의심 탐지 파이프라인

목표: 사용자의 복원/추가삭제가 **개인 취향이 아니라 보편적 버그로 보이는 패턴**을 자동으로
추려서, 조용히 묻히지 않고 개발자 눈에 띄게 한다. 이 파이프라인은 **어떤 경우에도 미래의 자동
CUT/KEEP 라우팅을 바꾸지 않는다** — 바꾸는 건 오직 개발자가 L0을 직접 수정했을 때뿐이다.

### 3.1 구조적 태그

각 NG 후보에 결정론적 feature extractor가 **구조적 태그**를 붙인다. 사람 취향과 무관하게 기계적으로
계산 가능한 특징만 쓴다.

| 태그 예시 | 계산 |
|---|---|
| `boundary_followed_by_connective` | wi_end 바로 다음 단어가 접속사 목록(그래서/근데/그러니까/그런데/그리고 등)에 속함 |
| `boundary_crosses_speaker_block` | 삭제 범위가 화자 블록 경계와 겹침 |
| `span_near_threshold` | 신뢰도가 라우팅 임계값(0.75/0.55)의 ±0.03 안에 있음 |
| `source_llm_wide_scan` | Stage 1 전체 스캔이 찾아낸 구간(이미 항상 flag되지만, 패턴 집계에도 씀) |
| (새 태그는 버그가 발견될 때마다 개발자가 추가) | |

태그는 **버그 후보를 찾기 위한 것**이지 분류 체계(A~F)를 대체하지 않는다. 케이스 taxonomy는 L0에
그대로 둔다.

### 3.2 의심 클러스터링

같은 구조적 태그를 가진 항목에 대해 사용자 결정이 **한쪽으로만** 쏠리면 "구조적 의심"으로 표시한다.

- **한 영상 안에서**: 같은 태그가 2회 이상 나오고 전부 같은 방향(전부 복원 또는 전부 추가삭제)
- **여러 영상에 걸쳐**: 같은 태그가 서로 다른 영상에서도 반복되면 신뢰도를 더 높임(이 사용자만의
  우연이 아니라는 근거)

**개인화와의 결정적 차이**: 이 집계는 `prefs.json`처럼 사용자별로 저장해 자동 적용에 쓰지 않는다.
그냥 로그 — `videos/<이름>/edit/structural_suspects.json`에 영상별로 남기고, 확정 시 콘솔/영수증에
"이런 패턴이 N번 반복됐습니다, 버그일 수 있어요"라고만 알려준다. 아무것도 자동으로 바뀌지 않는다.

### 3.3 개발자 트리아지 → L0 승격

```
[검토 중] 같은 구조적 태그로 2회 이상, 한쪽으로만 결정
   └─▶ structural_suspects.json에 기록 (자동 라우팅에 영향 없음)

[확정 시]
   └─▶ 영수증에 "구조적 의심 패턴 N건" 표시 + 상세 보기

[개발자 경로 — 유일한 "학습" 경로]
   구조적 의심 패턴 확인
   → 진짜 보편적 버그인지 판단 (한 사용자의 특이 취향이면 기각)
   → gold 반례 fixture 후보로 추가 (06-검증과-측정.md 손상 주입 세트)
   → L0 수정 (taxonomy 지시문, few-shot 예시, 또는 결정론적 규칙 — 예: §1의 접속사 안전망)
   → 회귀 게이트(BS145/167/183 재검증) 통과 후 배포 — 모든 사용자에게 적용
```

이전 설계의 "L2 → L0 승격" 개념은 유지하지만, **승격의 입구가 L2(개인별 few-shot 저장소)가 아니라
구조적 의심 큐**로 바뀐 것이 핵심이다. 개인화 저장소를 거치지 않으므로 "먼저 개인화로 흡수됐다가
나중에 승격"하는 단계가 사라지고, 버그는 발견 즉시 모두에게 적용될 후보가 된다.

## 4. L0 — 유일하게 바뀌는 층

이전 설계의 L0 구조는 그대로 쓴다. 개인화 층(L1~L3)이 사라졌을 뿐이다.

| 파일 | 내용 | 누가 바꾸나 |
|---|---|---|
| `rules/gates.yaml` | 관문 G1~G4 기준, 경계 보호 거리 | 개발자만, 회귀 게이트 필수 |
| `rules/defaults.yaml` | 라우팅 임계값, 쉼 목표치, 루프 반복 상한 | 개발자만, 회귀 게이트 필수 |
| `rules/fewshot_base.jsonl` | 단계별 기본 few-shot (구조적 의심에서 승격된 예시 포함) | 개발자만, 회귀 게이트 필수 |
| `rules/editorial.md` | 채널 편집 원칙 문장 | 개발자만 |

지금 스크립트에 흩어진 상수(`route_candidates.py`의 0.75, `plan_pauses.py`의 목표치,
`build_edl.py`의 15ms)를 이 파일들로 옮기는 것은 이전 계획대로 유효하다 — 개인화와 무관하게 "어떤
게 안전 관문이고 어떤 게 조정 가능한 기본값인지" 구분하는 것 자체는 여전히 필요하다.

## 5. few-shot — L2 검색은 당장은 유지 (계획 수정, 10-01)

**10-01 실측으로 계획 수정**: "사용자별 L2 사례 검색은 더 이상 호출하지 않는다"고 이 섹션에
처음 썼으나, `classify_region.py`의 `fewshot.retrieve()`를 실제로 제거하고 BS145+BS167로
gold 재검증한 결과 **BS167 재현율이 0.704~0.764 → 0.515로 폭락**(정밀도도 0.748→0.699) - 안전
지표(오삭제 flag 누락)는 0건으로 유지됐지만 놓치는 NG가 크게 늘었다. "개인화(사용자별로 다르게
적용되는 것)"와 "few-shot 예시 자체가 어려운 판정(특히 case B)에 기여하는 것"은 서로 다른
문제였는데, 전자를 없애려다 후자까지 같이 잃을 뻔했다 - `결정-이력.md` 10-01 항목. **그래서
`fewshot.retrieve()` 호출은 되돌려 살려뒀다.**

| 단계 | few-shot | 구성 |
|---|---|---|
| 4 화자 블록 줄 역할 | ✅ | L0 고정 예시만 |
| 5 NG 분류 | ✅ **핵심** | L0 고정 예시 + **L2 사용자 사례 검색 유지**(`fewshot.retrieve`, 아래 참고) |
| 7 전체 맥락 검토 | ✅ 소량 | L0 고정 예시만 |
| 10 이음새 교차 판정 | ✅ | L0 고정 예시만 |
| 11 PD 평가 | ✅ 규칙 위주 | 채널 편집 원칙 문장(`rules/editorial.md`)만 — 사용자별 복원 사례 요약은 제외 |
| 11 시청자 평가 | ❌ **의도적으로 제외** | 페르소나만 (기존과 동일) |

**남은 과제** (§1의 구조 결함은 여전히 유효 — 그래서 "그대로 유지"가 아니라 "재설계 과제"로 남김):
L2 사례 저장소(`~/.video-cut/cases/<user>.jsonl`)를 사용자별이 아니라 **공유 저장소**로 바꾸는
것을 다음 과제로 둔다(`남은-개발.md`). 공유 저장소면 재현율 기여는 그대로 가져가면서, §1이
지적한 문제(보편적 버그가 개인 계정에 묻혀 다른 사용자가 똑같이 겪음)는 구조적으로 사라진다 -
사례가 공유되므로 한 사용자가 겪은 패턴이 다음 사용자에게도 (좋은 쪽으로) 영향을 준다. 다만
"공유 저장소에 아무 사례나 바로 반영"도 다시 §1 같은 사고가 날 수 있으니, 반영 전 가벼운 승인
또는 구조적 의심 큐(3장)를 거치는 게 안전하다 - 구현 시 설계.

## 6. 열린 질문 — 확인 필요

1. **`_pref_action_for_case()`를 걷어낼 것인가**: 이미 라이브 코드이고 §1에서 지적한 결함을 그대로
   갖고 있다. "개인화를 전부 뺀다"는 이번 결정과 모순되므로, 이것도 제거하거나 최소한 더 이상
   확장하지 않는 것으로 명시해야 한다. 제거하면 지금 REVIEW 큐 기본값에 반영되던 소소한 편의가
   없어진다 — 트레이드오프를 사용자가 판단해야 함.
2. **`keep_words`(말버릇 유지) 같은 명시적 설정은 다른 범주인가**: "그니까"를 필러로 자르지 말라는
   설정은 통계로 *추론*된 개인화가 아니라 사용자가 *명시적으로* 입력한 설정이다. 버그/취향 구분
   문제가 애초에 없는 범주로 볼 수 있다 — 이런 명시적 설정(설정 화면에 사용자가 직접 입력)은
   남겨둘지, 아니면 "개인화는 전부 없앤다"는 원칙대로 이것도 빼고 채널 편집 원칙(`editorial.md`)에
   개발자가 직접 반영하는 방식으로 바꿀지 결정 필요.
3. **`fewshot.py`/`learn_from_session.py`/`pattern_suggest.py` 코드 자체**: 문서상 역할은 없앴지만
   코드가 아직 남아있다. 완전 삭제할지, 구조적 의심 큐 구현에 일부 재사용(패킷 로깅 부분)할지는
   구현 시 정할 것.

## 7. 여러 사용자

- 사용자 구분은 기존과 같다. 다만 이제 구분하는 이유가 "취향을 따로 쌓기 위해서"가 아니라
  "구조적 의심 집계를 사용자별로 섞으면 서로 다른 설치본의 버그가 뒤섞여 원인 추적이 어려워지기
  때문"이다.
- L0는 공유한다 — 유일하게 바뀌는 층이고, 바뀌면 모든 사용자에게 적용되므로 회귀 게이트를 반드시
  거친다.
