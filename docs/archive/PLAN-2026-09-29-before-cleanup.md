# 영상 자동 편집 파이프라인 기획

작성일: 2026-09-28
상태: 기획 확정 전 (미결 사항은 마지막 섹션 참고)

## 1. 목표

강의형 토킹헤드 원본(10~20분)을 넣으면 다음이 자동으로 처리된 상태로 Final Cut Pro 프로젝트가 열리는 것.

1. 컷편집 — 무음 구간, 추임새(아·어·음·그러니까), 말더듬, 재촬영(NG 테이크) 제거
2. 자막 — 한국어 문장형 자막, 편집 가능한 캡션 트랙으로
3. 자료 화면 — 발화 내용에 맞는 키워드 카드, 그래프, 논문 캡처, 삽화를 적절한 시점에 삽입
4. 음량 — 유튜브 표준 -14 LUFS 정규화

레퍼런스: 베싸TV (과학·논문 근거 기반 육아 강의 채널). 토킹헤드 + 문장형 자막 + 핵심 키워드 텍스트 + 논문/그래프 캡처 + 삽화 구성.

## 2. 핵심 결정

### 2.1 마무리는 사람이 한다 (B 안)

완전 자동 mp4 출력(A 안)이 아니라, 자동으로 러프컷을 만들고 Final Cut Pro에서 마무리한다.

- 이유: 강의 콘텐츠는 잘못 잘린 한 문장이 영상 전체 신뢰도를 깎는다. 자동화가 못 잡는 실수를 사람이 확인할 여지가 필요하다.
- 복구 가능성: FCPXML은 원본 파일의 구간 참조 목록이라 원본은 손상되지 않는다. 잘린 구간은 클립 경계를 트림하면 그대로 살아나고, 컷을 없애려면 두 클립을 이어붙이면 된다. 재렌더·재트랜스크립션 불필요.
- Final Cut Pro를 선택한 이유: FCPXML이 네이티브 포맷이라 호환이 가장 확실하고, 마커·캡션 트랙·connected clip·Roles를 모두 지원한다.

### 2.2 오케스트레이터: Claude Code + video-use 스킬

[browser-use/video-use](https://github.com/browser-use/video-use)를 베이스로 쓴다.

- 트랜스크립트 기반 편집: LLM이 영상을 프레임으로 보지 않고 단어 단위 타임스탬프가 달린 텍스트(~12KB)로 읽는다. 애매한 지점만 필름스트립+파형 PNG로 확인한다.
- 이미 갖춘 것: 단어 경계 컷, 30ms 오디오 페이드, 자막 최후 적용, 오버레이 슬롯 구조, 렌더 결과 자체 검증(self-eval) 루프, 세션 메모리(`project.md`).
- 없는 것 (직접 만들어야 함): 한국어 자막 스타일, 자료 화면 플래너, FCPXML export.

### 2.3 음성인식(ASR): ElevenLabs Scribe 권장

컷편집 품질은 ASR 정확도가 결정한다.

| 선택지 | 한국어 정확도 | 비용 | 비고 |
|---|---|---|---|
| ElevenLabs Scribe (권장) | WER 3.1%, 벤치마크 1위 | 유료 API | 단어 단위 타임스탬프, 화자 분리, 추임새 원문 유지 |
| mlx-whisper (로컬) | 양호하나 Scribe 대비 낮음 | 무료 | M4 Pro에서 로컬 실행 가능. 말더듬을 한 단어로 합치는 경향 → 추임새 제거 정밀도 하락 |

**결정: ElevenLabs Scribe 사용.** API 키는 `~/Developer/video-use/.env` 의 `ELEVENLABS_API_KEY=` 에 넣는다 (git 추적 제외됨, 권한 600). 무료 대안이 필요해지면 [freecut](https://github.com/Moh4696/freecut) 포크로 교체 가능.

### 2.4 컷편집 요구사항 (이전 프로젝트에서 검증된 원칙, 그대로 유지)

이전 Palmier 기반 파이프라인(`Reference/PROJECT_RESTART_GUIDE.md`)에서 확정된 편집 원칙. 기술 구현은 바뀌어도 이 요구는 바뀌지 않는다.

**(1) 무음은 지우는 게 아니라 리듬에 맞게 다듬는다**

| 문맥 | 목표 pause | 비고 |
|---|---|---|
| 일반 문장 사이 | 0.25초 (0.20–0.30) | |
| 나열 | 0.11초 (0.08–0.15) | 빠르게 |
| 인용 → 설명 전환 | 0.40초 (0.35–0.45) | 여유 있게 |
| 주제 전환 | 손대지 않음 | 의도된 호흡 |
| 질문 → 답변 | 손대지 않음 | 의도된 호흡 |

pause 문맥 분류는 LLM이 하되, 실제 삭제 프레임 계산은 결정론적으로 한다.

**(2) NG(재촬영)는 마지막 시도만 남긴다**
같은 내용을 다시 시작한 재시작 에피소드에서 시간상 마지막 시도가 최종본. 명시적 촬영 규칙. 후보는 45초 창 안에서 하나의 에피소드로 묶는다.

**(3) 반복은 NG가 아니다**
강조 반복("정말 정말"), 교육적 재진술, 정상 나열, 조사·어미만 바뀐 것("하나의 → 하나를")은 살린다. 단순 문자열 반복 제거가 아니라 의미 판단이 필요하다. 상세는 4장.

**(4) 정상 발화는 절대 잘리지 않는다 — 자동화율보다 우선**
- 발화 경계에 10~20ms(24fps 기준 2~3프레임) 여유를 남긴다
- 애매하면 덜 지운다
- dB 기준 무음 검출은 추정일 뿐. 숨소리·잡음과 말을 구별 못 하므로 최종 확정은 사람이 듣는다

**작업 방식 원칙 (계속 적용)**
- 계획과 실행 분리. 자동화는 계획만 만들고 실행은 사람 승인 후. AI는 라벨만 붙이고 실행 권한 없음
- 채택 기준은 "정확도가 올랐다"가 아니라 **"내가 검토할 건수가 줄었다"** (Jev 실험 보류 사유)
- 검토는 검토 대상만 모아서, 왜 봐야 하는지 등급이 붙은 상태로
- 이미 한 작업은 다시 하지 않고, 검증 실패 시 멈춘다. 자동 복구·추가 삭제 금지
- 사람이 정정한 사례는 쌓이되, 규칙 변경은 사람이 직접 승격

## 3. 파이프라인 — Claude 스킬 + 로컬 웹 검토 (2026-09-28 재설계)

### 3.1 제품 형태

이 프로젝트는 **Claude Code 스킬**로 배포한다 (`~/.claude/skills/video-cut` 심링크, video-use와 같은 방식). 자체 완결형 — video-use 등 외부 스킬에 의존하지 않는다.

**사용자 절차:**
```
videos/                          ← 지정 공간
  └─ 20261002_자존감/             ← 사용자가 만든 폴더 (이름 자유)
       ├─ raw.mp4                 ← 원본만 넣는다
       └─ (스킬 실행 후 생성)
            edit/clean.mp4        ← tmcd·메타데이터 제거본 (FCP 호환 + 브라우저 즉시 재생)
            edit/transcript.json
            edit/candidates.json  ← 자동 처리 결과 (NG·화자 이탈·무음)
            edit/decisions.json   ← 웹에서 확정한 최종 결정 (재현 가능한 기록)
            20261002_자존감.fcpxml ← Final Cut Pro에 넣을 결과
            preview.mp4           ← 렌더링 미리보기 (기본 켬)
```

`/video-cut 20261002_자존감` → 자동 처리 → 브라우저에 검토 화면 → 확정 → 폴더에 결과.

### 3.2 처리 흐름

```
raw.mp4
  ├─ 0. 정리          clean_media.py: tmcd/data 트랙·메타데이터 제거, faststart (스트림 복사, 무손실)
  ├─ 1. 트랜스크립션  ElevenLabs Scribe, 단어 단위 (자체 구현, 캐시)
  ├─ 2. 자동 처리     ── 전부 자동으로 "적용된 상태"로 만든다. 사람은 예외만 본다 ──
  │     ├─ NG 판별     후보 탐지 → LLM 분류 → 라우팅 (4장). AUTO_SAFE는 삭제 적용, REVIEW는 강조
  │     ├─ 화자 이탈   주 화자 아닌 구간을 블록으로 묶어 "전체 삭제 제안" (4.6a)
  │     └─ 무음 리듬   단어 사이 쉼을 문맥별 목표치로 다듬는 트림 계산 (2.4 표). 전역 프리셋, 항목별 검토 없음
  ├─ 3. [웹 UI]       로컬 서버 + 브라우저. 여기가 유일한 판단 지점 (3.3)
  ├─ 4. 확정          decisions.json 기록 → 아래 셋을 폴더에 생성
  │     ├─ FCPXML      확정 컷만 반영된 깨끗한 타임라인 (복구용 컷 마커만 선택적)
  │     ├─ preview.mp4 720p 하드웨어 인코딩 (M4 Pro 기준 1분 내외), 기본 켬
  │     └─ 결정 기록   모든 수정이 gold 데이터로 자동 축적 → 다음 영상 few-shot
  └─ (다음 단계, 같은 웹 화면에 얹음) 자막 → 자료 화면 → 엔딩 아웃테이크 코너
```

**Final Cut Pro의 역할이 바뀐다:** 컷 판단은 웹에서 끝난다. FCP는 자막 스타일·자료 화면 배치·색 같은 마무리만 한다. 마커 기반 검토(이전 5장)는 폐기 — "검토 대상 표시"는 되지만 "검토를 빠르게" 만들지 못한다는 게 실측으로 확인됨(48개 마커 = 결국 타임라인 전체를 훑어야 함).

### 3.3 웹 검토 화면 — "다 안 보게" 만드는 장치

트랜스크립트가 곧 타임라인이다. 영상을 보며 판단하지 않고, **텍스트 위에서 판단하고 소리로 확인**한다.

1. **3단계 텍스트**: 단어마다 살림(보통) / 자동 삭제(취소선·흐림) / 확인 필요(노란 강조). 취소선 클릭 → 복원, 드래그 선택 + Delete → 삭제, 경계는 단어 단위 드래그. 자동 삭제분은 행동 없이 눈으로 훑는 것만으로 검증됨
2. **검토 큐**: 노란 항목만 순서대로. 항목당 한 줄 근거 + 재생 + 살림/삭제. 키보드: `Space` 듣기, `K` 살림, `C` 삭제, `J`/`←` 이동. 전체 대본은 문맥 참고용일 뿐 읽지 않는다
3. **이음새 듣기**: 항목 재생 = 컷 직전 몇 단어 + 컷 직후 몇 단어를 이어서 재생. 진짜 질문은 "지워도 되나"가 아니라 "지운 뒤 자연스러운가". 지워질 부분은 별도 버튼
4. **가상 재생(렌더링 없음)**: 브라우저가 clean.mp4를 직접 재생하며 잘린 구간을 건너뜀. 즉시, 컷 지점에 수십 ms 멈칫함. 검토엔 충분
5. **무음은 슬라이더**: 2.4의 목표치를 전역 프리셋으로. 미리듣기 후 통째 적용. 예외(주제 전환의 긴 쉼)만 "의도적 쉼 유지"로 표시. 이번 샘플 기준 검토 48건 → 11건으로 줄어드는 지점
6. **화자 이탈은 블록 하나**: "카메라 밖 대화 141초 — 전체 삭제 [승인] [펼치기]". 펼치면 화자별 줄 단위 살림
7. **모든 수정 = 정답 데이터**: 단어 ID + 원래 라벨 + 최종 결정을 기록. 상단에 "이번 영상 검토 N건 (지난 영상 M건)" — 채택 기준(검토 건수 감소)을 UI가 직접 보여줌
8. **아웃테이크 별표**: 잘린 NG에 별표 → 엔딩 코너 후보 (4.4a-1에서 발견한 채널 스타일)

### 3.3a 사용자 피드백 반영 (2026-09-28 저녁)

1. **오른쪽 큐 패널 폐기** — "결국 다 봐야 한다"는 문제는 큐로도 해결되지 않았음. 본문 하나가 편집기. `J`가 다음 미결 항목을 본문에서 바로 선택
2. **표시는 세 가지만**: 잘림(취소선) / 삭제 제안(노란 점선, 결정 필요) / 유지. 자동·수동·대화 구간의 구분은 팝업의 이유 문구에만 남기고 색으로 구분하지 않음. 대화 구간 라벨은 "삭제 제안 N줄 [제안대로 삭제] [전부 살리기]"
3. **드래그 = 삭제/살리기 한 동작**: 선택 상태에 따라 기본 버튼이 바뀜(살아있으면 삭제, 잘려있으면 살리기). 취소선 클릭은 덩어리 전체 선택. `⌘Z` 되돌리기(같이 바뀐 결정까지 복구)
4. **쉼은 게이지**: 단어 사이 0.12초 이상 모든 쉼을 길이에 비례한 막대로. 채워진 만큼 남기고 빈 만큼 잘림. 드래그로 0(삭제)~전체(유지) 조절, 더블클릭 = 추천값, 상단 목표치를 바꾸면 모든 추천값이 따라 바뀜. 0.12초 기준은 Scribe 타임스탬프 오차(50~100ms) 때문 — 그 밑은 쉼이 아니라 발음 간격. BS145: 쉼 1,540개(0.35초 이상은 LLM 분류 277개, 나머지는 일반)
5. **이음새 페이드**: 가상 재생은 컷 지점 앞 40ms 음량 감소 → 점프 → 60ms 복귀. FCPXML은 컷마다 3프레임(0.1초) 크로스 디졸브(`--transition-frames`, 효과 uid `FxPlug:4731E73A-8DAC-4113-9A30-AE85B1761265`), 양쪽 핸들이 있을 때만. 미리보기 렌더는 구간마다 30ms 오디오 페이드. **디졸브 포함 FCPXML의 Final Cut 임포트 검증은 미완료**(테스트 파일 `videos/BS145/edit/xfade_test.fcpxml`, 사용자 확인 대기) — 실패 시 `--transition-frames 0`

### 3.4 구현 형태

- 백엔드: Python 표준 라이브러리 HTTP 서버 (Range 요청 지원 — 브라우저 영상 탐색에 필수). 기존 `scripts/*.py`가 그대로 처리 단계
- 프론트엔드: 단일 HTML + vanilla JS. 2,500단어 대본은 그냥 띄우면 됨
- 서버는 스킬이 띄우는 독립 프로세스. 확정 버튼이 서버에서 직접 FCPXML·미리보기를 생성 — Claude가 사이에 끼지 않음
- 이전 프로젝트 `ng-review-app`(단어 경계 드래그 + 오디오 미리듣기)이 같은 UX 결론에 도달했던 선례

## 4. NG 판별 설계 — 컷편집의 핵심

NG를 잘 찾는 것이 컷편집 품질의 대부분을 결정한다. 원칙은 "잘라야 할 재시작"과 "살려야 할 반복"을 구분하는 것이며, 그 판단의 중심은 **내용(의미) 비교**다.

### 4.1 케이스 분류

| 케이스 | 정의 | 판단 근거 | 처리 |
|---|---|---|---|
| A. 실수 → 제대로 말하기 | 앞 시도에 오류(잘못된 단어·숫자·문장 붕괴)가 있고 뒤에서 고침 | 두 시도의 내용이 **충돌**. 편집어("아니", "어") 동반 잦음. 수정 단어에 음향 강조 마킹 | 앞 시도 삭제 |
| B. 말하기 → 더 잘 말하기 | 앞 시도도 틀리지 않았지만 같은 내용을 더 잘 설명하려고 다시 말함 | **두 시도의 내용이 같은지를 실제로 확인**한다. 같은 내용의 재진술이면 NG, 새 정보가 추가·확장된 것이면 NG가 아님 | 같은 내용 → 앞 시도 삭제 / 다른 내용 → 유지 |
| C. 강조 반복 | "정말 정말", "많이 많이" 같은 의도적 반복 | 어휘 범주(부사·형용사·감탄), 두 반복의 운율이 평행, 사이 쉼이 짧음 | 유지 |
| D. 교육적 재진술 / 정상 나열 | "다시 말하면", "즉", "첫째·둘째" 등 담화 흐름 안의 반복 | 담화 표지 동반, 피치 리셋 없음, 문장 완결 후 이어짐 | 유지 |
| E. 형태론적 수정 | 조사·어미만 바뀜 ("하나의 → 하나를") | 어간 동일, 변경 폭이 접사 수준. 문장 재시작이 아니라 단어 하나 수정이므로 재시작 에피소드로 묶지 않고 별도 처리 | **경계가 깨끗하면 틀린 단어 삭제** (앞 단어 뒤 쉼 ≥ 0.15초, 고친 단어가 완전한 단어로 인식됨) / 붙여 말했으면 REVIEW. 정책값 `E_policy = CUT_IF_CLEAN`으로 두고 오삭제 발생 시 `KEEP`으로 전환 가능 |
| F. 미완성 후 방향 전환 | 문장을 버리고 전혀 다른 내용으로 넘어감 | 앞 조각이 미완결, 뒤와 내용 무관 | 앞 조각 삭제 (재시작이 아니라 단순 중단) |

**B 케이스가 가장 어렵고 가장 중요하다.** 문자열 유사도로는 못 잡는다. LLM이 두 시도를 읽고 "전달하려는 정보가 동일한가"를 명시적으로 판정해야 한다.
- 같은 내용: 주장·수치·대상·결론이 같고, 뒤 시도가 더 정돈되었거나 길거나 짧을 뿐 → NG
- 다른 내용: 뒤 시도가 새 근거·예시·조건을 추가하거나, 앞 시도가 이미 완결된 문장으로서 뒤와 역할이 다름 → 둘 다 유지
- 판정 불가: 사람 검토로

### 4.2 판별 신호 — 텍스트 + 음향 + 영상

연구와 업계 모두 텍스트 단독보다 다중 신호 결합이 확실히 낫다고 결론. 이전 프로젝트는 텍스트와 dB만 썼으므로 여기가 가장 큰 개선 여지.

**텍스트 (단어 단위 트랜스크립트)**
- 두 시도 전문과 앞뒤 ±3문장 문맥
- 편집어 유무 ("아니", "어", "그러니까", "다시")
- 어휘 범주 (강조 부사인가), 조사·어미만 다른가
- 담화 표지 ("다시 말하면", "즉", "첫째")
- 앞 시도의 문장 완결 여부, 단어 절단 여부
- **내용 동일성 판정** (B 케이스 핵심)

**음향 (단어 타임스탬프 기준으로 계산, librosa / parselmouth)**
- 후보 경계 앞뒤 쉼 길이
- 재시작 첫 단어의 F0 리셋 (문장 첫머리 높은 피치로 돌아감 → 재시작)
- 두 시도의 F0 곡선 유사도 (평행 → 강조 반복)
- 수정 단어의 에너지·길이 증가 (실수 수정 마커)
- 앞 시도 마지막 단어의 절단

**영상 (후보 경계 프레임 2~3장을 LLM에 제시) — 선택적, 테스트 후 결정**
- 시선이 카메라를 벗어남 (대본 확인)
- 자세·표정 리셋
- 손·머리 움직임 급증

비용·시간 추정 (15분 강의, NG 후보 50개 가정, Claude Opus 5 기준 $5/$25 per MTok):

| 구성 | 후보당 입력 | 영상 1편 비용 | 소요 시간 |
|---|---|---|---|
| 텍스트+음향만 | ~2K 토큰 | 약 $0.9 | 1~2분 (병렬 호출) |
| + 프레임 3장 (1280×720, 장당 ~1.2K 토큰) | ~5.7K 토큰 | 약 $1.8 | 2~3분 (프레임 추출 30초 포함) |

Sonnet 5로 내리면 절반 이하, Batch API(50% 할인)는 시간이 급하지 않을 때 적용 가능. 즉 영상 신호를 켜도 편당 $1 안쪽의 추가 비용이라 **비용은 결정 요인이 아니다.** 판단 기준은 REVIEW 건수가 실제로 줄어드는지 여부.

**출처 상태**
- 후보 단어가 현재 소스에 전체/부분/미확인으로 남아 있는지 (이전 프로젝트 오류 9건 중 7건의 원인)

### 4.3 판별 파이프라인

```
1. 후보 탐지 (결정론적, LLM 없음)
   45초 창 안에서 단어열 유사도 + 접두사 일치로 재시작 후보 클러스터 생성
   → 이전 프로젝트 detect_restarts.py 로직 이식

2. 증거 수집 (후보마다 4.2의 신호 전부를 구조화)

3. LLM 분류 (Claude, 구조화 JSON 출력, 실행 권한 없음)
   입력: 문맥 + 증거 + 본인 정정 사례 few-shot 10~20개
   방식: "화자가 의도한 최종 대본"을 먼저 복원 → 실제 트랜스크립트와 대조
         (판단 단위를 "이 단어를 지울까"가 아니라 "최종 대본에 이 문장이 어떤 모습인가"로)
   출력: 케이스 라벨(A~F), 내용 동일성 판정(B), 삭제 범위(단어 ID), 복원 대본, 근거, 신뢰도

4. 신뢰도 라우팅
   AUTO_SAFE:  텍스트·음향·영상 신호가 모두 한 방향, 신뢰도 높음, 알려진 오류 패턴 아님
   REVIEW:     신호가 갈림 / B 케이스 내용 판정 애매 / 알려진 오류 패턴 해당
               (혼합 span, 주변 재시작 혼동, 단일 단어 반복, 부분 잔존)
   KEEP:       C·D로 판정 (E는 경계 상태에 따라 AUTO_SAFE 또는 REVIEW)

5. 사람 검토 (Final Cut Pro 타임라인 마커 + 검토 목록)
   → 정정 결과를 gold에 append → 다음 편집의 few-shot에 자동 반영
   → 규칙 변경은 사람이 승격
```

"의도한 대본 복원 → 대조" 방식은 Descript, TimeBolt, Vizard 등 업계 도구가 쓰는 접근이며, 이전 프로젝트의 "혼합 span", "주변 재시작 혼동" 오류를 구조적으로 피한다.

### 4.4a 원본↔편집본 정렬로 gold 데이터 자동 생성

사용자가 준비한 3종 영상:

| 영상 | 역할 |
|---|---|
| 샘플 영상 원본 | 편집 전 날것. NG 판별 로직의 테스트 입력 |
| 샘플 영상 편집본 | 사람이 실제로 편집한 결과 = 정답지 |
| 타겟 영상 | 로직 검증 후 실전 적용할 대상 (정답 없음) |

원본과 편집본을 둘 다 트랜스크립션한 뒤 단어열을 정렬(sequence alignment, 예: difflib/Levenshtein)하면 편집본에서 빠진 원본 구간이 그대로 드러난다. 이걸 자동으로 라벨링한다:

```
원본 트랜스크립트 ──┐
                    ├─ 단어열 정렬 (원본 vs 편집본)
편집본 트랜스크립트 ─┘
        │
        ├─ 편집본에 남은 구간   → NOT_NG (유지된 것)
        └─ 편집본에서 빠진 구간 → 후보 (아래로 분기)
                │
                ├─ 빠진 구간이 4.1의 A/B 패턴(재시작 클러스터 안)과 겹침 → NG로 자동 라벨
                ├─ 빠진 구간이 pause 조정 폭 안에 있음(수 프레임)      → 무음 다듬기로 라벨, NG 아님
                └─ 그 외(설명이 안 되는 삭제)                          → 사람 확인 필요 목록으로
```

이렇게 만든 gold는 이전 프로젝트 gold(82건, 다른 촬영분)보다 **이번 촬영 스타일과 편집 취향에 직접 맞는 정답**이라 우선순위가 높다. 두 gold를 합쳐서 few-shot과 회귀 테스트에 쓴다.

주의: 편집본에서 빠졌다고 전부 NG는 아니다 — 자막 삽입 공간 확보, 순수 호흡 정리, 콘텐츠 판단(주제 자체를 들어냄) 등 NG와 무관한 삭제도 섞여 있을 수 있다. 자동 라벨링은 "왜 빠졌는지" 패턴이 분명한 것만 확정 라벨을 주고, 애매하면 사람 확인으로 보낸다.

3. 사용자가 `BS145_raw.mp4`를 Import Media로 직접 시도 → **목록에 안 뜨고 드래그도 안 됨** → XML과 무관하게 **원본 파일 자체를 FCP가 미디어로 인식 못 함**이 드러남
4. `ffprobe -show_streams`로 원인 확인: video/audio 외에 **`tmcd`(QuickTime 타임코드) data 트랙**이 있었음 (일반적으로는 무해하지만 이 파일에서는 FCP의 미디어 인식을 막음)
5. 로컬에 FCP 설치 후 `open`으로 직접 실행 + `osascript`(System Events accessibility API)로 임포트 결과 대화상자를 텍스트로 직접 읽는 자동 진단 루프 구축 → 사용자 왕복 없이 반복 테스트 가능해짐
6. `ffmpeg -map 0:v:0 -map 0:a:0 -map_metadata -1 -c copy -movflags +faststart`로 tmcd 트랙과 메타데이터를 완전히 제거한 재무싱본(`BS145_raw_clean.mp4`, 화질 손실 없음, 스트림 복사) 제작 → **오류 없이 임포트 성공**
7. 디버깅 도중 별도로 발견·수정한 실제 FCPXML 버그 2건(정리해서 재사용): `<sequence>`에 `audioLayout`/`audioRate` 누락 시 `format` 참조가 "예기치 않은 값"으로 실패 → 추가로 해결. `<asset>`에 `videoSources`/`uid`, `<asset-clip>`에 `format` 추가(문제 해결에 필수는 아니었으나 실제 Apple 내보내기 형식과 일치시킴)

**결론: 원본 영상의 `tmcd` 트랙이 근본 원인.** XML 구조는 처음부터 대부분 맞았음. 최종 검증: 컷 17개 + 마커 65개(컷 17 + 검토 48) 포함 완전판이 정리본 기준 오류 0건으로 임포트됨. 상대 경로(포터블) 버전도 재확인 완료.

**파이프라인에 반영할 것:** FCPXML export 전에 항상 `-map_metadata -1`로 소스를 정리하는 단계를 표준 전처리로 추가해야 함 (ASR/video-use는 tmcd와 무관해 영향 없었음 — FCP 임포트에만 해당). `scripts/export_fcpxml.py`는 정리본을 가리키도록 사용.

**산출물**: `Reference/vidoes/BS145_raw_clean.mp4`(FCP 호환 정리본), `Reference/vidoes/BS145_rough_cut.fcpxml`(최종, 상대 경로, Final Cut Pro에서 임포트 검증 완료) 산출물은 `Reference/gold_data_v2/`(BS145 기준 이번 촬영 스타일 gold v1) — 이전 프로젝트 gold(`Reference/gold_data/`, 다른 촬영분)와 별도 보관, 둘 다 few-shot·회귀 테스트에 사용.

**해결됨 (2026-09-28):** 17:08~17:19 구간은 편집 실수가 아니라 **아웃테이크/비하인드 모음 코너**. 편집본 16:59~17:03("오늘은 여기까지. 공부하는 엄마의 근거 있는 육아정보, 베싸였습니다")가 채널 고정 클로징 멘트이고, 그 직후 이어지는 "나단이엘 발음" NG 구간에 `[웃음]` 오디오 이벤트가 2회 포함되어 있어 의도적 편집으로 확인. 원본 영상 확인 불필요, 트랜스크립트의 audio_event 태그와 클로징 멘트 위치만으로 판단 가능했음.

**설계 시사점:** 본편 NG는 컷으로 제거하되, 제거된 NG 일부(특히 웃음 포인트)를 영상 끝에 별도 코너로 재구성해 보여주는 게 이 채널의 편집 스타일일 수 있다. 지금 파이프라인(4장)은 "NG를 지운다"만 다루는데, 이 채널을 정확히 재현하려면 "지워진 NG 중 일부를 엔딩 코너용으로 후보 추림" 단계가 추가로 필요할 수 있음 — 자막·자료화면 단계(6~9)와 함께 나중에 사용자와 확인.

**추가 검증 (편집본 11:20 전후, 사용자 제보):** 물건 떨어지는 소리("우당탕탕")만 잘리고 대사는 안 끊긴 구간 발견. 원본 확인 결과 raw 1022~1026초 "지식은 신념이 되고 신념은," 완전 중복(유사도 1.0, 최초 규칙만으로도 NG_CANDIDATE 확정)과 정확히 겹침 — 소리에 놀라 문장을 재시작했고, 그 재시작이 이미 정확히 잡혀 있어서 소음도 함께 제거됨. 추가 조치 불필요.

**알려진 한계 (기록만, 지금 단계에서 대응 안 함):** 위 사례는 "소음 → 화자가 놀라서 재시작"이라 텍스트 재시작 신호로 우연히 잡혔다. **화자가 끊김 없이 말을 이어갔다면 단어 diff 기반 파이프라인은 이런 소음을 원리적으로 못 잡는다** — 텍스트가 그대로면 신호가 없기 때문. 사용자 확인: 이런 경우는 드묾. 빈도가 낮아 지금은 별도 오디오 이상탐지(에너지 스파이크 스캔)를 추가하지 않음. 빈도가 늘면 4.2의 음향 신호 레이어에 "텍스트 변화 없이 발생하는 순간적 에너지 급증" 탐지를 추가하는 것을 재검토.

### 4.4 정확도 개선 계획

- **이전 프로젝트 gold 데이터 이식**: 확정 NG 22 에피소드, 사람 정정 9건, `ng-reviewed-cases.jsonl`. few-shot과 회귀 테스트로 즉시 사용
- **알려진 오류 패턴 4종 반례 fixture**를 회귀 게이트에 포함
- **측정 지표**: AUTO_SAFE 비율 ↑ 와 정상 발화 오삭제 = 0 을 동시에. 둘 중 하나만 좋아지면 채택 안 함
- **장기**: 정정 데이터가 수백 건 쌓이면 소형 분류기 파인튜닝 검토 (연구상 도메인 주석이 충분하면 few-shot LLM과 동등 이상)

### 4.5 촬영 단계 신호

재촬영 직전에 "다시" + 2초 쉼을 두는 습관을 들이면 A·B 케이스 대부분이 결정론적으로 잡히고, LLM은 진짜 애매한 경우(무표시 재시작 vs 강조 반복)에만 쓰인다. 가이드: [`docs/촬영-가이드.md`](docs/촬영-가이드.md).

**설계 제약: 신호가 없는 영상도 동일하게 편집 가능해야 한다.** 기존 촬영분에는 신호가 없다. 후보 탐지 단계에서 명시적 신호("다시"+쉼, 손뼉)가 있으면 우선 적용해 AUTO_SAFE로 올리고, 없으면 4.3의 전체 파이프라인으로 판별한다. 신호는 정확도를 올리는 가산 요소이지 전제 조건이 아니다.

### 4.6a 전체 맥락 검토 패스 (신규 — 화자 이탈·PD 가이드 대응)

샘플(`BS145_raw.mp4`)의 원본↔편집본 정렬(4.4a)에서 발견: 전체 삭제 구간(221초) 중 **64%(141초)** 가 4.1의 재시작 패턴이 아니라, 화면 밖 PD/코치가 실시간으로 지도하고 화자가 같은 문장을 다시 찍는 구간이었다. 이 구간은 "재시작처럼 보이는가"로 접근하는 국소(local) NG 탐지로는 원리적으로 못 잡는다 — 반복이 아니라 **흐름 이탈**이기 때문이다. 사용자 확인: PD 가이드가 실제로 존재하며, 빈도는 낮지만 대비가 필요함.

4.1~4.3의 파이프라인은 이 문제를 상향식(단어열에서 재시작 후보를 찾음)으로 접근하는데, PD 가이드는 하향식(전체 흐름을 보고 이질적인 구간을 찾음) 체크가 따로 있어야 구조적으로 커버된다. 두 체크는 독립적으로 돌려서 서로의 사각지대를 메운다.

**(1) 화자 기반 결정론적 사전 필터**
주 화자(전체 분량 기준 가장 말이 많은 화자)가 아닌 사람의 구간은 그 자체로 강한 신호. NG 재시작 여부와 무관하게 우선 플래그해서 아래 2번 입력에 포함.

**(2) 전체 맥락 검토 (신규 단계)**
후보 단위가 아니라 **영상 전체의 패킹된 트랜스크립트(화자·타임스탬프 포함)를 한 번에** LLM에 보내, 화자 수와 무관하게 "강의 흐름과 무관한 구간"을 찾는다.
- 대상: 촬영 관련 대화(구도·시선·발음 지도), 잡담, 장비/타이밍 지시, 메타 발언("여기 봐봐", "다시 갈까요")
- 출력: 구간(시작~끝 단어 ID), 사유, 권장 처리(CUT_CANDIDATE / REVIEW), 신뢰도
- 국소 재시작 탐지(4.3)와 **독립적으로** 실행 — 결과를 합쳐서 라우팅(4.3의 5단계)에 반영
- 비용: 영상당 1회 호출(후보별 호출이 아님). 5천 단어 트랜스크립트 ≈ 7천 토큰, Opus 5 기준 편당 $0.1 이하로 무시할 수준

**설계 원칙:** 화자 전환·흐름 이탈이 있는 구간은 전부 이 패스가 1차로 넓게 표시하고, 최종 CUT은 여전히 사람 승인을 거친다(2.4 작업 방식 원칙과 동일). 빈도가 낮다는 이유로 생략하지 않는다 — 있을 때 놓치면 방송 불가 수준의 실수가 되기 때문.

**구현 결과 (`detect_speaker_blocks.py`, 2026-09-28):** BS145 코칭 구간(198.9~355.8초, 44줄)을 블록 하나로 검출. 줄별 역할 라벨: 지시 38 / 재시도 4 / 최종 1 / 내용 2 — 살리는 줄(241.7 "셀리그만 교수에 따르면…", 249.9~257.0 내용)이 **편집자가 실제 살린 줄과 완전히 일치**, 삭제 86초. 검토 큐에서는 이 157초 구간이 항목 하나(승인/펼치기)로 처리된다. 주의: 화자 라벨은 구간마다 바뀌므로 "말이 적은 화자"가 아니라 "대화 형태"로 검출해야 한다(3장 6번 참조).

### 4.6 근거 연구

- Levelt (1983) *Monitoring and self-repair in speech* — 수정의 3단계 구조(중단 → 편집어 → 수정)
- Levelt & Cutler (1983) *Prosodic marking in speech repair* — 실수 수정에는 운율 마킹, 표현 개선에는 없음 (A/B 구분 근거)
- Girand et al. *Classifying repeated words as planned or unplanned* — 어휘 범주로 강조 반복 97% 구분
- Zhang (2020) *The Prosody of Fluent Repetitions* — 유창한 반복은 쉼 길이·F0 곡선으로 구분
- Romana et al. (2023, ICASSP/TASLP) — 텍스트+음향 결합이 단일 모달보다 우수, ASR 품질이 텍스트 기반 상한
- Wu et al. (2026) — LLM 자기 수정 검출 F1 0.73; 도메인 주석 충분하면 소형 파인튜닝 모델 동등
- *Self-repair in Korean conversation* (East Asian Pragmatics) — 한국어 조사·어미 교체형 수정 (E 케이스 근거)

## 5. 출력 사양

### 5.1 FCPXML (Final Cut Pro 12.3에서 임포트 검증 완료)

- 메인 스토리라인: 확정된 컷만 반영된 클립 시퀀스. **clean.mp4를 상대 경로로 참조** — fcpxml과 같은 폴더에 두면 어느 컴퓨터에서든 열림, 원본은 한 프레임도 손상 없음(트림으로 복구 가능)
- 마커: 검토 마커 없음(검토는 웹에서 끝남). 복구용 컷 마커(무엇이 왜 잘렸는지)만 선택적
- 버전: `1.11` (12.3에서 검증). `--fcpxml-version`으로 변경 가능
- 검증된 필수 속성: `<sequence>`에 `audioLayout`/`audioRate` (없으면 format 참조가 "예기치 않은 값"으로 실패), `<format>`에 `colorSpace`, `<asset>`에 `videoSources`/`uid`. 시간은 전부 정수 프레임 × frameDuration의 유리수
- (다음 단계) 캡션 트랙: 자막을 편집 가능한 캡션으로 / Connected clip: 자료 화면 / Roles: 대화·자막·자료화면 분리

### 5.2 preview.mp4 (기본 켬)

720p, 하드웨어 인코딩(videotoolbox), 구간별 추출 → concat. M4 Pro에서 24분 영상 기준 1분 내외. 확정 직후 백그라운드 생성. FCP 없이 결과를 처음부터 끝까지 볼 때, 다른 사람에게 공유할 때 사용.

### 5.3 decisions.json

모든 컷의 최종 상태(단어 ID 범위, 종류: NG/무음/화자이탈, 원래 자동 라벨, 사람이 바꿨는지, 아웃테이크 별표). 같은 raw.mp4로 동일 결과를 재생성할 수 있고, 사람이 바꾼 항목은 다음 영상의 few-shot·회귀 테스트에 자동 편입된다.

## 6. 한국어 자막 스타일

video-use 기본값은 영어 2단어 대문자 스타일이라 새 스타일이 필요하다.

- 청크: 4~7어절, 자연스러운 쉼(≥0.3s)과 문장 부호에서 끊기
- 폰트: Pretendard (또는 사용자 지정)
- 위치: 하단, MarginV 60~80
- 강의형에 맞춘 가독성 우선 (큰 폰트, 외곽선)
- 파이널컷 캡션으로 넘기므로 스타일은 최종적으로 FCP에서 조정 가능

## 12. 컷편집 자체 value-up 기획 (2026-09-29)

11장은 컷편집 *이후* 단계다. 지금 당장 중요한 건 컷편집 파이프라인(4~9장) 자체의 품질·효율을 높이는 것. 코드(`scripts/*.py`)를 확인해 실제로 빠진 지점 위주로 정리.

### 12.1 추임새(필러) 단독 제거 — §1 목표인데 미구현

§1 목표 1번에 "무음 구간, 추임새(아·어·음·그러니까), 말더듬, 재촬영 제거"라고 명시했지만, 실제 구현(`detect_ng_candidates.py`)은 **재시작 클러스터 안에 딸린 편집어만** 본다(4.1 A/B 케이스의 보조 신호). 재시작 없이 단독으로 나오는 "음...", "그니까", "어 그래서"류 필러는 지금 파이프라인에서 어디서도 잡히지 않는다.

- 설계: 별도 결정론적 탐지 패스 — 정해진 필러 어휘 목록 + 품사/문맥(문장 시작 또는 쉼 직후, 뒤에 실질적 내용이 이어짐)으로 후보 추출
- 화자 말버릇일 수 있어 완전 자동 삭제는 위험 → 기본은 REVIEW, 반복 승인되면 해당 화자 한정으로 AUTO_SAFE 승격 (12.3의 규칙 승격 UI와 연결)
- 가치: §1에 적어놓은 목표와 실제 구현의 간극을 메우는 것 — 지금 상태로는 "말더듬·재촬영은 잡지만 추임새는 안 잡는" 반쪽 구현

### 12.2 오디오 이상탐지로 텍스트 사각지대 메우기

§4.4a-1 "알려진 한계"에 스스로 기록한 문제: 화자가 끊김 없이 말을 이어가면 소음(물건 떨어지는 소리 등)이 있어도 **단어 diff 기반 파이프라인은 원리적으로 못 잡는다.** 지금은 "빈도가 낮아 대응 안 함"으로 보류된 상태.

- 저비용 안전장치: librosa로 에너지 스파이크(RMS 급증)만 스캔 — 텍스트 변화와 무관하게 발생하는 순간을 REVIEW 큐에 "소음 후보"로 추가만 함 (자동 삭제 아님, §2.4 원칙)
- LLM 호출 없이 결정론적 신호이므로 비용 거의 없음. 빈도가 실제로 낮으면 REVIEW 건수에 거의 영향 없고, 있으면 방송 사고를 막는 안전망
- §4.2에 설계는 이미 있음(F0·에너지) — 지금 안 쓰고 있는 신호를 이 용도로만 좁게 먼저 켜보는 것

### 12.3 검토 결정 승격 UI — "검토 건수"보다 "검토 시간" 줄이기

§2.4에 "규칙 변경은 사람이 직접 승격"이라는 원칙은 있지만, 그 승격이 **어떻게** 일어나는지는 설계돼 있지 않다. 지금 리뷰 큐는 항목을 하나씩 처리하는 구조라, 같은 패턴(예: E케이스 조사·어미 수정)이 10개 몰려 있어도 10번 반복 클릭해야 한다.

- 검토 화면에 "이 결정 이후로도 같은 패턴에 적용" 버튼 추가 → 같은 세션 내 나머지 동일 패턴 항목에 일괄 반영 + 다음 영상 few-shot에 우선순위 태그로 기록
- 채택 기준 자체를 "검토 건수"에서 "검토에 걸린 시간/클릭 수"로 보강 — 건수가 줄어도 패턴이 묶여있지 않으면 체감 시간은 안 줄 수 있음
- 배치 승격은 4.4a-1에서 실측된 "REVIEW 48건 중 41건이 사실 두 가지 패턴(PAUSE_OR_TIGHTEN, MULTI_SPEAKER)"이라는 관찰과 같은 방향 — 이미 종류별로 묶이는 경향이 있다는 게 실측으로 확인됨

### 12.4 45초 창 밖의 재시작 — 먼 거리 재촬영

`detect_ng_candidates.py`의 재시작 클러스터링은 45초 창 안에서만 동작한다(§2.4-2 "45초 창 안에서 하나의 에피소드로 묶는다"). 촬영을 멈췄다가 몇 분 뒤 같은 문단을 통째로 다시 찍으면 이 창을 벗어나 애초에 후보에 잡히지 않는다 — 검토 큐로도 안 가고 조용히 최종본에 두 버전이 다 남는 실패 모드.

- 문장/문단 단위 임베딩 유사도로 전체 트랜스크립트에서 "내용이 겹치는 먼 거리 쌍"을 찾는 별도 저빈도 패스 (영상당 1회, §4.6a의 전체 맥락 검토와 같은 방식으로 비용이 낮음)
- 45초 창 로직과 독립적으로 실행해 사각지대를 메움 (4.6a와 같은 "상향식 vs 하향식 이중 체크" 패턴 재사용)

### 12.5 few-shot을 정적 슬라이스에서 검색 기반으로

§4.3 3단계는 "본인 정정 사례 few-shot 10~20개"를 쓴다고만 되어 있고, gold 데이터가 커질수록(현재 이전 프로젝트 82건 + 정정 9건 + BS145분 신규) 어떤 10~20개를 고르는지가 분류 정확도를 직접 좌우한다. 지금처럼 고정 슬라이스면 데이터가 쌓여도 그 이득이 프롬프트에 반영 안 될 수 있음.

- 후보의 임베딩(또는 케이스 라벨+문맥 키워드)으로 gold에서 유사 사례만 검색해 few-shot에 넣기
- 회귀 테스트(12.6)와 짝을 이뤄야 의미 있음 — 검색 방식 바꿀 때마다 AUTO_SAFE 비율·오삭제 0건 여부를 비교해야 안전하게 개선 가능

### 12.6 자동 회귀 게이트

§4.4에 "측정 지표"(AUTO_SAFE 비율 ↑, 정상 발화 오삭제 = 0)는 정의돼 있지만 자동화된 실행 장치가 없다. 프롬프트나 라우팅 임계값을 하나 바꿀 때마다 사람이 감으로 판단하는 중 — 지금 규모(BS145 하나)에선 괜찮지만 few-shot과 규칙이 늘어날수록 회귀 위험이 커짐.

- gold 데이터(§4.4a, `Reference/gold_data*`) 전체를 한 번에 돌려 AUTO_SAFE/REVIEW/오삭제 건수를 비교하는 스크립트 하나(`scripts/regression_check.py` 등)
- 프롬프트·임계값 변경 PR마다(또는 그냥 로컬 습관으로) 돌려서 §4.4 지표가 실제로 개선됐는지 확인. 인프라성 투자지만 이후 모든 변경의 안전판

### 우선순위 제안

가장 비용 대비 효과가 큰 건 **12.2(오디오 이상탐지, 결정론적·거의 공짜)**와 **12.1(필러 제거, §1 목표 간극 메움)**. **12.3(승격 UI)**은 사용자가 매 영상 반복 작업을 느끼기 시작하면 그때 체감 가치가 커짐. 12.4~12.6은 인프라성 투자로, gold 데이터와 실전 영상 편수가 늘어나는 시점에 맞춰 착수하는 게 맞음.

## 13. LLM 적극 활용 재설계 — 구현 완료 (2026-09-29)

"컷편집을 텍스트+음성 기반으로 하니 LLM을 더 적극 활용하면 성능이 좋아질 것"이라는 방향에 따라, §4.2에 설계만 되어 있던 음향 신호와 §4.3에 설계만 되어 있던 few-shot을 실제로 프롬프트에 태우고, 로컬 규칙의 구조적 사각지대(45초 창 밖 재시작, 대화 형태 아닌 화자 이탈)를 메우는 전체 맥락 패스와 확정 전 자기검증 패스를 추가했다. BS145 실데이터로 전부 실행 검증함.

### 13.1 모델 선택 (비용 대비 효율)

작업 난이도에 맞춰 세 단계로 나눴다. 전부 하드코딩된 `claude-opus-5`였던 것을 작업별로 재배정.

| 단계 | 파일 | 모델 | 근거 |
|---|---|---|---|
| 쉼(pause) 문맥 분류 | `plan_pauses.py` | **Haiku 4.5** | 담화 표지("다시 말하면", "첫째")로 대부분 판별되는 고빈도 단순 분류. 틀려도 삭제되는 건 침묵뿐, 말은 안 지워짐 |
| NG 케이스 분류(A-F) 기본 | `classify_candidates.py` | **Sonnet 5** | 표준 의미 판단. 후보 대부분(C/D/명백한 A)은 이 tier로 충분 |
| NG 케이스 분류 - B케이스, 저신뢰도 | `classify_candidates.py` | **Opus 5 (에스컬레이션)** | §4.1 "B 케이스가 가장 어렵고 가장 중요하다" - Sonnet 결과가 B이거나 confidence<0.80이면 Opus로 재판정. 쉬운 다수는 싼 모델, 진짜 어려운 것만 비싼 모델 |
| 화자 블록 줄별 역할(지시/재시도/최종) | `detect_speaker_blocks.py` | **Sonnet 5** | "어느 시도가 최종본인가" 판단은 NG A/B와 같은 급의 의미 판단이라 Haiku로 안 내림 |
| 전체 맥락 검토(신규) | `whole_context_review.py` | **Opus 5** | 영상당 1회 호출, 품질이 비용보다 중요 (§4.6a: 편당 $0.1 이하로 결정 요인 아님) |
| 자기검증(신규) | `self_critique.py` | **Sonnet 5** | 영상당 1회, "명백히 어색한가"만 확인 - Opus 급 판단 불필요 |

### 13.2 실제로 구현한 것

- **`scripts/prosody.py` (신규, 12.A)**: librosa로 단어별 F0·에너지를 실제로 계산해 `edit/prosody.json`에 저장. `classify_candidates.py`가 이걸 읽어 "재시작 후보 첫 단어 F0가 화자 평균보다 몇 배 높은가", "두 시도의 F0 곡선이 평행한가(강조 반복 신호)", "이어지는 구간 에너지가 몇 배 큰가(수정 강조 마킹)"를 자연어 근거로 번역해 프롬프트에 넣음. 로컬 연산, API 비용 없음. BS145 전체(24분)에 21초 소요
- **few-shot 6개를 `CASE_TAXONOMY`에 직접 추가**(12.B) - 이전엔 0개였음
- **`scripts/whole_context_review.py` (신규, 12.C/4.6a 2번 단계)**: 영상 전체 트랜스크립트를 한 번에 Opus에 보여 "45초 창 밖의 먼 거리 재진술"과 "대화 형태가 아닌 독백형 화자 이탈"을 찾음. 항상 REVIEW로만 라우팅(자동 삭제 없음)

- **`classify_candidates.py` 병렬화(12.E)**: `ThreadPoolExecutor`로 후보를 동시에 분류

- **의존성 추가**: `librosa` (pyproject.toml)

### 13.3 구현 중 발견·수정한 버그 3건 (실데이터 검증으로 확인)

1. **인덱스 불일치**: `classify_candidates.py`의 자체 `load_words`가 `type != "spacing"`로 필터링해 `detect_ng_candidates.py`(`type == "word"`만 사용)와 다른 인덱스 공간을 썼다. 오디오 이벤트 태그(`[웃음]` 등)가 있는 구간에서 문맥이 조용히 어긋날 수 있었던 잠재 버그. `common.words_only` 재사용으로 통일해 수정
2. **`claude-sonnet-5`의 기본 extended thinking이 `max_tokens`를 전부 소진**: `self_critique.py` 실제 호출에서 `parsed_output=None, stop_reason="max_tokens"`로 확인. 구조화 출력을 쓰는 모든 호출에 `thinking={"type": "disabled"}` 추가로 해결(비용도 같이 줄어듦 - 안 쓰는 thinking 토큰이 안 나감)
3. **`librosa.load`가 mp4 컨테이너를 직접 못 읾음**: `clean.mp4`에 `LibsndfileError: Format not recognised`. `transcribe.py`가 이미 하던 대로 ffmpeg로 wav 추출 후 로드하도록 수정

### 13.4 실데이터 검증 결과 (BS145)

- **음향 신호가 실제로 판단에 쓰임**: "오늘 영상은, 오늘 영상은" 후보를 분류하며 LLM이 "피치 리셋이 동반되어 두 번째 시도가 실제 발화 시작"이라고 직접 근거로 인용 - 설계만 있던 신호가 실제로 판단에 반영됨을 확인
- **전체 맥락 검토가 로컬 규칙이 전혀 못 보던 걸 찾음**: 영상 시작의 "큐."(클래퍼보드 신호)와 끝의 "컷!"(촬영 종료 지시)을 OFF_TOPIC으로 검출 - 기존 45초 창 기반 재시작 탐지·대화형 화자 이탈 탐지 둘 다 구조적으로 놓치던 구간
- **자기검증이 실제로 어색한 컷 1건을 찾아 REVIEW로 강등**: "이런 의사결정을 내릴 때" 앞뒤가 대구 표현 중 하나만 남아 불완전하다고 판단
- **모델 티어링·병렬화·에스컬레이션 정상 동작 확인**: 샘플 3건 중 2~3건이 신뢰도 기준 미달로 Opus 에스컬레이션됨 (설계대로 "쉬운 건 싼 모델, 어려운 건 비싼 모델")

## 14. 사용자 프로세스(리뷰 화면)에 LLM 추가 적용 (2026-09-29)

컷편집 알고리즘이 아니라 **사람이 검토하는 웹 화면 자체**에 LLM을 추가로 붙임.

### 14.1 패턴 일반화 제안 (`scripts/pattern_suggest.py`)

같은 NG 케이스를 같은 방향(삭제/유지)으로 3번 연속 결정하면(`MIN_TRIGGER`), 그게 우연이 아니라 일반화 가능한 규칙인지 LLM이 판단해 파란 배너로 제안한다. "이후 이런 패턴은 자동으로 처리할까요?"에 사용자가 예/아니오를 눌러야만 적용됨 - LLM은 제안만 하지 실행하지 않는다(2.4 원칙 그대로). `server.py`의 `_maybe_suggest_pattern`/`apply_suggestion`이 훅.

실측(BS145): case F(미완성 전환) 3건을 연속 CUT 처리하니 4번째 남은 후보("뜻--")를 정확히 짚어 "문장을 시작하다 완성하지 못하고 끊긴 뒤 전혀 다른 내용으로 다시 시작하는 미완성 발화는 삭제"라는 규칙을 제안, confidence 0.82.

### 14.2 트랜스크립트 검색 (`scripts/transcript_search.py` + 사이드바 검색창)

리터럴 문구는 브라우저에서 즉시(무료, 서버 호출 없음) 찾는다. 못 찾으면 서버가 전체 트랜스크립트를 의미 기반으로 검색한다("화자 이탈만", "셀리그만 이야기하는 부분" 같은 질의). Enter로 다음 결과 이동, Esc로 초기화.

### 14.3 `claude -p`로 전환 — API 키 대신 기존 Claude Code 구독 사용

사용자가 "이미 Claude를 과금해서 쓰고 있다"고 확인 - 14.1/14.2는 `Anthropic()` API 클라이언트 대신 `scripts/claude_cli.py`를 통해 로컬 `claude -p`(Claude Code CLI 헤드리스 모드)를 서브프로세스로 호출한다. 별도 `ANTHROPIC_API_KEY` 없이 이미 쓰는 Claude Code 로그인/구독으로 인증됨.

**실측 트레이드오프:**
- 사소한 요청 하나에도 ~5.5초 (API 직접 호출은 thinking 끄면 1~2초) - CLI가 매번 Claude Code 전체 시스템 프롬프트를 새로 로드하고, thinking을 끄는 CLI 플래그가 없음
- 실제 검색 요청(트랜스크립트 전체 포함)은 ~15초
- 응답이 외부 JSON 봉투(`result` 필드) + 마크다운 코드펜스로 이중 래핑되어 나와 파싱을 한 겹 더 해야 함(`claude_cli.call_json`이 처리)

**그래서 적용 범위를 나눔:** 14.1/14.2는 세션당 드물게(패턴당 1회, 리터럴 검색 실패 시에만) 호출되므로 이 지연이 감내 가능. 반면 영상당 30건 이상 도는 배치 파이프라인(`classify_candidates.py`, `plan_pauses.py`, `whole_context_review.py`, `self_critique.py`, `detect_speaker_blocks.py`)은 그대로 Anthropic API 직접 호출 유지 - 같은 방식으로 바꾸면 영상 1편 처리가 (현재 ~2분에서) 수십 분으로 느려짐. 결국 같은 Anthropic 인프라를 쓰는 건 동일하고 과금 방식(구독 사용량 vs 토큰당 과금)만 다르므로, "버튼 클릭처럼 드문 호출"과 "영상당 배치 호출"을 기준으로 나눈 것.
