# 검증 결과 (BS167, 원본 29:50)

상태: ✅ 정답지 대조 완료 (2026-09-30). BS145 이후 처음 돌린 **두 번째, 독립적인** 영상 — 임계값 일반화 확인용. 화자 이탈(카메라 밖 대화) 블록 0건이라 BS145와 편집 패턴 자체가 다름.

정답지: `videos/BS167/BS167_raw.mp4`(원본) 전사 ↔ `BS167_final.mp4`(완성본, 사용자 제공) 별도 전사을 diff해 얻은 실제 삭제 단어 목록. 파이프라인 전체(`run.py`와 동일 단계, 서버만 생략)를 raw에 그대로 적용한 뒤 `eval_against_gold.py`로 대조.

## 최대 삭제 + 이음새/전체 루프 (2026-09-30)

| 측정 | 값 | BS145 대비 |
|---|---|---|
| 자동이 지운 구간 | 66개, 218.5초 | 34개, 224.6초 |
| 사람이 지운 구간 (정답지) | 76개, 286.1초 | 65개, 220.5초 |
| 정밀도 (TP=226 FP=110) | 0.673 | 0.675 (거의 동일) |

| **재현율, FN 정제 후** (편집상 변경 18건 제외) | **0.511** | **0.718** |
| **오삭제 중 flag 없이 조용히 잘린 것** | **0단어, 0구간** | **0건 (유지)** |

**핵심**: 안전 지표(경고 없는 복원 0건)는 두 번째, 완전히 다른 영상에서도 그대로 지켜졌다 — 최대 삭제 방침의 핵심 약속("위험한 것은 반드시 표시한다")이 BS145 한 편의 우연이 아니라는 근거. 정밀도도 거의 동일(0.673 vs 0.675)해 "잘못 자르는 비율"은 안정적이다.

**재현율은 크게 떨어졌다** (0.718 → 0.511, FN 정제 후). 즉 BS167에서는 사람이 실제로 지운 것 중 자동이 놓친 게 BS145보다 훨씬 많다 — 검토 화면에서 사용자가 직접 더 잘라야 하는 항목이 늘어난다는 뜻(단, 잘못 잘리는 위험이 커진 건 아님). 원인 후보:
- **전체 맥락 검토(`whole_context_review.py`)가 거의 안 잡음**: raw findings 1건(그나마 로컬 패스가 이미 커버) — BS145는 이 패스가 "큐", "컷!" 등 몇 건을 잡아냈던 것과 대조적. 화자 이탈 블록이 없는 영상이라 이 패스가 기대만큼 일반화 안 됐을 가능성
- **로컬 NG 탐지 창(window)이 놓친 반복이 많음**: FN 44건(진짜 놓친 NG) 중 다수가 case B(반복) — 재시작과 재진술 사이 간격이 로컬 탐지기의 비교 범위를 넘어서는 경우로 보임(`detect_ng_candidates.py` 자체 한계, `docs/현재-설계/NG-판별.md` 참고)

### 대안 선택(확장/축소) 안전성

1차 패스에서 65개 이음새 중 21개가 원안에서 경계가 바뀜(확장·축소·스냅). G2 재전사: 1차 64개 검사 0건 의심 → 전체 루프 재투입 후 65개 검사 4건 의심, 전부 flag로 잡혀 화면에 뜸(조용히 넘어간 것 없음). `QUIET_MARGIN_DB`(BS145 실측 기반 잠정값)를 그대로 썼는데도 안전망이 뚫리지 않아, 이 값 때문에 다른 영상에서 문제가 생긴다는 증거는 아직 없다.

## 결론

두 번째 영상으로 확인해야 했던 미결 사항 3건 중 2건 해결:
- `QUIET_MARGIN_DB` 일반화: ✅ 문제 없음
- 확장 대안 선택 안전성: ✅ 문제 없음
- 영상 프레임 신호 채택 여부: 이번 실행으로는 판단 불가(신호 자체를 아직 구현 안 함, `docs/백로그/영상-프레임-신호.md`)

**새로 발견한 이슈**: 재현율이 영상마다 크게 흔들린다(0.718 → 0.511). 안전(오삭제 0)은 지켜지지만, 검토 부담(더 많이 직접 잘라야 함)이 영상 특성에 따라 커질 수 있다 — 특히 화자 이탈 블록이 없는 영상에서 전체 맥락 검토 패스의 효과가 약해지는 것으로 보임. 정식 대응은 `docs/기획/06-검증과-측정.md`의 임계값 보정 절차로, 세 번째 영상이 더 쌓이면 판단하는 게 안전(표본 2편으로 임계값을 바꾸면 과적합 위험).

## 후속: `whole_context_review.py` 재설계 2차례 (같은 날)

사용자 요청("LLM 활용을 늘려야, 내용을 이해해야")에 따라 재현율 저하를 파고든 기록. 상세 경위는 `결정-이력.md` 참고, 여기는 수치만.

| 버전 | 정밀도 | 재현율(정제) | 오삭제(flag없이) | 비고 |
|---|---|---|---|---|
| v1 (09-29, 단일 호출+힌트) | 0.673 | 0.511 | 0건 | 원래 버전 |
| v2 (09-30, map-reduce claim 비교) | 0.631 | 0.534 | 0건 | 채택·현재 라이브 상태 |
| v3 (09-30, +local_restarts) | 0.499 | 0.447 | 0건 | **되돌림** - 근본 원인은 정확히 찾았으나 통합 결과가 악화 |

**v3에서 밝혀진 진짜 근본 원인**: gold FN 53건의 85%(45건)가 "먼 곳의 재진술"이 아니라 `detect_ng_candidates.py`의 `has_internal_repetition`이 딱 3단어 앞까지만 봐서 통째로 후보 생성 단계에서 빠진 것 — 실제 패턴은 "그래서, 그래서 제 친구는... 그래서 제 친구는 아이를 데리고 계단 쪽으로..." 식 문장 하나를 2~4번 고쳐 말하는 같은 문단 안의 재시작 사슬(FN 52건 중 36건이 서로 60단어 이내로 몰려 있음). 이 진단에 맞춰 map 단계에 local_restarts를 추가해 16건(고신뢰도 10건)을 정확히 새로 찾아냈지만(정성적 성공), 후보가 72→90건으로 늘자 `assemble_draft.py`의 병합과 `seam_refine.py`의 최대삭제 대안선택이 상호작용해 새 후보와 무관한 기존 컷 100여 단어까지 다르게 처리되며 정밀도·재현율이 함께 나빠졌다 — 안전(0건)은 안 깨졌지만 채택 기준 미달로 코드는 v2로 되돌림.

**다음 시도가 참고할 것**: 후보 밀도가 높아질 때 `assemble_draft.py`/`seam_refine.py`의 병합·대안선택이 왜 무관한 기존 결정까지 흔드는지가 진짜 남은 문제 - `whole_context_review.py` 쪽이 아니라 그 두 파일을 봐야 한다.

위에서 "재현율이 영상마다 크게 흔들린다"고 남긴 문제는 결국 국소 3단어 창이 같은 문단 재시작
사슬을 못 잡는 상향식 구조 자체가 원인이었다(사용자 제안, `결정-이력.md` 09-30 "하향식 재설계").
`detect_ng_candidates.py`/`classify_candidates.py`/`whole_context_review.py`(위 v1~v3 전부)를
`detect_regions.py`(Stage 1, 전체를 넓게)+`classify_region.py`(Stage 2, 부분을 좁게)로 교체,
`route_candidates.py`의 `KEEP_CONFIDENCE_MIN`도 0.80→0.55로 재하향, `global_review.py`도 1회
통독으로 단순화한 뒤 BS167을 처음부터 깨끗하게 재실행:
